# FDA 483 OCR 판독 개선 — 벤치마크·채택안·클라우드 설계 (2026-10-28)

> 상태: **2차 판독(tesseract CLI) 채택·구현** · 클라우드 OCR/LLM 비전은 **설계만**(계정·키 필요 — 사용자 승인 후 연동).
> 구현: `collect_fda_483._second_chance_ocr` / `_reocr_483_pdf_text` · 테스트: `tests/test_fda483_ocr_second_chance.py`.

## 1. 벤치마크 세트

| 세트 | 구성 | 출처 |
|---|---|---|
| 판독 실패 | Supabase `raw_signals`(source='FDA 483') 중 **findings 0건 + `fda483_excerpt` 있음 47건** 전수. 그중 이미지가 없는 디지털 원본 3건(106455·195404·195573 — 파서 문제)을 빼 **44건**을 OCR 벤치 모집단으로 썼다 | 원본 = raw_json `pdf_url` |
| 정상 판독 대조군 | findings ≥1 문서 60건(`md5(document_id)` 순 무작위). 그중 스캔본(1차 OCR 이 실제로 도는 문서) 11건을 엔진 비교의 회귀 세트로 따로 봤다 | 동일 |

측정 지표: 관찰 추출 수(`_extract_483_observations_from_text`) · 공개 게이트 통과 수(`_is_publishable_deficiency` — 추출 단계에서 이미 적용) · 깨짐(`_deficiency_garble` 기호 0·조각률 ≤0.08 인 관찰 수, `_text_corruption_ratio`) · 쪽당 시간.

### 1.1 실패 원인 분류(가장 중요한 발견)

| 원인 | 건수 | 설명 |
|---|---|---|
| **FDA 가 넣은 깨진 텍스트층** | 28 | Adobe Acrobat "Paper Capture" 로 OCR 된 스캔본. 텍스트층이 `Sl'FEET AOOIIE$,S`·`I. Records…`(1.→I.) 처럼 깨졌는데 글자가 많아 `_needs_ocr` 가 "본문 있음"으로 판정 → **우리 OCR 이 한 번도 안 돌았다** |

## 2. 엔진·설정 비교 (판독 실패 44건, 이미지 페이지 전부 재판독, 136쪽)

"관찰>0 문서"는 운영과 같은 **폴백 규칙**(기존 산출 0건일 때만 새 판독 채택)으로 센 값이다. 시간은 4프로세스 병렬 부하 하 쪽당 값(상대 비교용). 대조군 열은 스캔 대조군 11건(기준 46관찰)을 같은 설정으로 강제 재판독했을 때의 관찰 수다.

- **idle 단일 프로세스 실측(20쪽):** 내장 경로 **4.15s/쪽**, CLI **3.41s/쪽**, CLI+OpenMP 4스레드 3.73s/쪽(이득 없음). 다른 프로세스와 CPU 를 나누는 상황에서 OpenMP 를 켜 두면 1쪽이 120s 타임아웃까지 늘어나는 것을 실측해 CLI 는 `OMP_THREAD_LIMIT=1` 로 고정했다.
- **기울기 보정**은 시험하지 않았다 — 순수 파이썬으로는 현실적인 속도가 안 나오고 numpy/opencv 의존성이 필요하다. tesseract 자체가 소각도 기울기를 흡수하며, 원본 대부분이 평판 스캔이다.
- **오픈소스 신경망 엔진**(PaddleOCR·docTR): CPU 1쪽 30s 이상 → 일일 예산 200쪽이면 100분으로 `grm-intake.yml` 55분 타임아웃을 넘는다. 설치 크기도 onnxruntime+opencv+모델 ≈ 650MB(venv 실측)이고 `requirements.txt` 에 ==pin 해야 할 전이 의존성이 10개 이상 늘어난다. **비채택.**
- 내장 경로와 CLI 가 같은 fast 모델인데 결과가 다른 이유: PyMuPDF 휠은 자체 빌드한 tesseract 를 번들하고, 페이지를 텍스트층으로 재구성해 붙이는 경로라 레이아웃 분석 입력이 다르다. CLI 쪽이 문서 5건 더 회수했다.

## 3. 채택안 — 관찰 0건 문서만 2차 판독

```
_fetch_fda483_pdf_text
  ├─ 텍스트층 추출 → _needs_ocr? ── 예 → 1차 OCR(PyMuPDF 내장, 현행 그대로)
  └─ 결과 텍스트 → _second_chance_ocr
        관찰 ≥1 → 그대로 반환(정상 문서 바이트 불변)
        관찰 0  → 이미지 페이지를 tesseract CLI 로 재판독(텍스트층 무시)
                   관찰 ≥1 → 재판독 텍스트, status `pdf-ok-ocr`
                   관찰 0  → 원래 텍스트·status 그대로(산출 축소 금지)
```

- **왜 폴백인가:** FDA 텍스트층을 일괄로 다시 읽으면(강제 재판독) 실패 44건 중 17건이 회수되지만 **대조군 60건 중 8건이 관찰을 잃었다**(92522 15→5 등 — Adobe 판독이 우리 판독보다 나은 문서가 있다). 관찰 0건 문서에만 닿게 하면 대조군 영향은 구조적으로 0이다.
- **왜 1차 OCR 엔진은 그대로 두는가:** 1차 엔진을 CLI 로 바꾸면 이미 관찰이 나오는 스캔본 1,500여 건의 텍스트가 재수집·재회수 때 바뀐다(스캔 대조군 195470 3→2). 이득은 폴백만으로 거의 다 얻는다.
- **엔진·모델 정본:** `.github/actions/setup-ocr` 가 이미 apt `tesseract-ocr`(바이너리)+`tesseract-ocr-eng`(fast)를 설치·검증한다(`command -v tesseract`). 워크플로 6종은 변경 없음. 바이너리가 없으면 2차 판독만 건너뛴다(`scan-ocr-unavailable:tesseract-cli`, 1차 산출 보존).

### 3.1 전후 실측(실제 `_fetch_fda483_pdf_text`, 원본 PDF 로컬 대체)

| 세트 | 수정 전 관찰>0 문서 / 관찰 | 수정 후 | OCR 쪽 |
|---|---|---|---|
| 판독 실패 47 | 0 / 0 | **22 / 60** | 31 → 167(+136) |
| 대조군 60 | 60 / 369 | 60 / 369(**전 문서 관찰 목록 동일**) | 62 → 62 |

회수 22건: 104952 · 111291 · 120720 · 136641 · 161809(10) · 161811 · 164192 · 167686 · 170260 · 188080 · 190693 · 191121 · 195435 · 195455 · 195596 · 195650 · 70085 · 79336 · 79806 · 82880 · 83098 · 97849(8). 60개 중 58개가 회수 경로용 엄격 게이트(`_is_recovered_deficiency_publishable`)도 통과한다.

### 3.2 시간·예산

- 2차 판독은 **1차 OCR 과 같은 페이지 예산**(`_OCR_BUDGET`: 일일 200쪽 · 월요일 버스트 600쪽 · 회수 600쪽)과 문서당 30쪽 상한을 쓴다. 따라서 **최악 벽시계는 변하지 않는다**(예산 200쪽 × 4.15s ≈ 14분, CLI 쪽은 더 짧다) — `grm-intake.yml` 55분 타임아웃·월요일 마감(06:45 KST, `FDA483_BURST_DEADLINE_EPOCH`)의 기존 계산이 그대로 유효하다.
- 일일 실측(grm-intake 최근 7회, 10-20~10-27): OCR **71·200·195·200·119·200·117쪽**, 수집 스텝 14~27분. 관찰 0건(본문 있음) 신규 문서는 하루 0~7건 → 2차 판독 추가분 ≈ **하루 0~25쪽(≈1~1.5분)**. 예산이 차는 날(7회 중 4회)은 그만큼 1차 OCR 대상이 다음 날 예약 회수(`recoverable`)로 밀린다.
- 관측: 수집 로그 `2차판독=채택/시도`, health `fda_483_ocr.reocr_tried`·`reocr_adopted`.

### 3.3 과거 결손 47건 반영

코드 머지 후 `grm-fda483-ocr-recovery.yml` 을 **`missing-observations` 모드로 dispatch**(apply)하면 같은 `_fetch_fda483_pdf_text` 를 타므로 위 22건이 회수된다(dry-run 먼저 권장).

## 4. 남은 한계

- **판독 실패 22건(44건 중)은 여전히 0건.** 대부분 1차·2차 모두 본문은 읽히는데 관찰 마커/번호가 깨지거나(`|.`·`wnfee)ossenven`) 옛 양식(번호 목록)이라 파서의 몫이다 — 관찰 파서는 다른 세션 범위라 손대지 않았다.
- **현행 공개 게이트를 통과하는 OCR 잡음이 있다**(이 PR 이 게이트를 바꾸지는 않았다 — 1차 OCR 경로에도 같은 한계가 있다): 79336 "WHOM REPORT IS ISSUED ~ ae : STAEET ADDRESS ~ …"(양식 머리말이 관찰 표제로 잡힘), 82880 "Your qualified Supervisery personne | is not revicwine…", 161811 "Devialbon investigations are inadeguate", 70085 "There has been vo Lest method…". 82880·79806 은 식품(달걀) 실사라 범위 게이트에서 빠진다. 2차 판독 텍스트(`pdf-ok-ocr`)에 엄격 게이트를 거는 것은 파서 측 후속 과제로 남긴다.
- 원본 144dpi 스캔의 정보 한계 — 업스케일·이진화로 회수 문서 수가 늘지 않았다.

## 5. 클라우드 OCR · LLM 비전 (설계만 — 미연동)

### 5.1 코드 경로(제안)

`_second_chance_ocr` 뒤 **3차 판독**으로 둔다 — 2차까지 관찰 0건인 문서만, 별도 예산 `FDA483_CLOUD_OCR_PAGE_BUDGET`(기본 0 = 꺼짐)으로. 같은 폴백 규칙(관찰이 나올 때만 채택, 아니면 원래 텍스트)과 같은 status(`pdf-ok-ocr`)를 쓰고, 제공자는 `FDA483_CLOUD_OCR_PROVIDER` 하나로 고른다. 시크릿이 없으면 클린 skip(`scan-ocr-unavailable:cloud-<provider>`). 페이지 이미지는 `page.get_pixmap(dpi=300)` PNG 를 그대로 보낸다(이미 공개된 FOIA 문서라 개인정보 이슈는 실사관 실명 정도 — 이미 공개분).

| 제공자 | 호출 | 필요한 시크릿(GitHub Actions) | 새 의존성 |
|---|---|---|---|
| Google Cloud Vision `DOCUMENT_TEXT_DETECTION` | REST `images:annotate`(API 키) | `GCP_VISION_API_KEY` | 없음(`requests`) |
| Google Document AI Enterprise OCR | REST `processors/{id}:process` | `GCP_DOCAI_SERVICE_ACCOUNT_JSON`, `GCP_DOCAI_PROCESSOR`(projects/…/locations/…/processors/…) | `google-auth`(==pin) — 서비스계정 토큰 |
| AWS Textract `DetectDocumentText` | 동기 API(쪽 단위) | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION` | `boto3`(==pin) — SigV4 |
| Azure Document Intelligence `prebuilt-read` | REST analyze(비동기 폴링) | `AZURE_DOCINTEL_ENDPOINT`, `AZURE_DOCINTEL_KEY` | 없음(`requests`) |
| Claude 비전(전사 전용 프롬프트) | Messages API, 이미지 블록 | `ANTHROPIC_API_KEY` | `anthropic`(==pin) |

권장 순서: **Azure Read 또는 Cloud Vision**(키 하나·새 의존성 0) → 필요 시 LLM. LLM 전사는 "보이는 글자 그대로, 고치지 말 것"을 강제해도 오탈자를 **자연스럽게 고쳐 쓰는**(원문 변형) 위험이 있어, 규제 원문 인용 용도에는 OCR 엔진을 우선한다.

### 5.3 승인 시 할 일

1. 제공자 선택 → 계정 생성·키 발급 → 위 이름으로 저장소 시크릿 등록.
2. 3차 판독 구현(기본 꺼짐) + 벤치 세트(이 문서 §1) 재측정으로 회수 증분·오탈자율 확인.
3. 회수 워크플로에서 먼저 켜고(예산 작게), 대조군 회귀 0 확인 후 일일 수집에 확대.

## 6. 재현

벤치 하네스는 저장소 밖(세션 스크래치)에서 돌렸다 — 핵심 절차만 남긴다: ① 위 SQL 로 대상 `document_id` 추출 ② `https://www.fda.gov/media/{id}/download` 로 원본 수령 ③ `http_get_bytes` 를 로컬 바이트로 대체하고 `_fetch_fda483_pdf_text` → `_extract_483_observations_from_text` 실행(수정 전 = `main` 워크트리, 수정 후 = 이 브랜치) ④ 엔진 비교는 이미지 페이지를 강제 재판독하며 엔진·모델(`tessdata_fast`/`tessdata_best`/legacy)·DPI·psm·전처리를 바꿔 같은 지표로 집계.
