# 기준 조항 원문 가독성 시안

**추천안은 브라우저에서 본문을 찾고, 빌드에서 기존 용어 규칙으로 풀이 위치를 정하는 방식입니다.** 두 기능 모두 정적 페이지에서 동작합니다.

## 오프라인 데모

`demo.html`을 브라우저에서 열면 됩니다. 같은 폴더의 JS 두 개를 그대로 두세요. 입력 HTML 두 장은 각각 102,937바이트(21 CFR 211.22), 94,417바이트(21 CFR 1271.180)입니다. 그중 211.22의 제목·경로와 국문 참고 번역 및 영어 원문의 문단 전체를 사용했습니다. 검색은 이 두 본문을 위에서부터 훑습니다. 용어사전의 `quality-control-unit` 항목에서 한·영 쉬운 정의를 가져왔으며, 데모에서는 괄호 속 약어를 뺀 표면형을 각 본문에서 사용합니다.

- `품질관리부서` 또는 `QUALITY CONTROL UNIT`으로 찾아 보세요. 입력한 뒤 첫 결과로 이동하며, 이전·다음과 Shift+Enter·Enter로 양끝을 순환합니다. 검색창은 페이지 안에서 열려 있고 브라우저의 Ctrl+F는 평소처럼 쓸 수 있습니다.
- 밑줄이 있는 품질관리부서와 quality control unit은 각각 첫 등장에 풀이가 붙습니다. 마우스를 올리거나 Tab으로 초점을 두면 열립니다. 탭이나 클릭으로 고정하며 같은 곳을 다시 누르거나 바깥을 누르면 닫힙니다. Escape로도 닫힙니다.
- 문단은 기존 항 번호와 순서를 유지하면서 내어쓰기로 항 시작을 찾기 쉽게 했습니다. 향후 항 번호를 강조하려면 번호의 문자와 공백을 유지한 채 확실히 구분되는 접두부만 표시합니다. 깊은 하위 항 들여쓰기는 좁은 화면에서 본문 폭과 함께 검토합니다.

## 구현 방식 비교

| 기능 | 순수 JS 클라이언트 | 빌드 시 서버 렌더 |
| --- | --- | --- |
| 페이지 안 찾기 | 본문 문단별 텍스트와 DOM 위치를 한 번 모아 두고 입력마다 문자열을 찾습니다. 인라인 요소를 가로질러 강조할 수 있고 중첩 결과도 각각 셉니다. | 정적 빌드는 방문자가 입력할 검색어를 알 수 없습니다. 빌드에서 본문·오프셋 색인을 미리 넣어도 입력, 강조, 이동에는 JS가 필요하고 HTML과 색인 크기 및 위치 동기화 비용이 늘어납니다. |
| 용어 풀이 | JS가 언어별 용어와 정의를 받아 각 문단에서 찾고 표시합니다. 데모에서는 쉽게 시험할 수 있고, 운영에서는 Python과 JS 두 규칙을 맞춰야 하며 사전 전체를 보내면 전송량이 늘어납니다. | 기존 매칭 코드로 각 문단의 용어를 골라 트리거와 일치한 정의만 HTML에 넣습니다. JS는 열기와 닫기만 담당하며 매칭 정책이 한곳에 남습니다. 문서 빌드 시간과 페이지별 마크업 증가량은 측정이 필요합니다. |

검색은 입력의 양끝 공백을 제거하고 ASCII 영문 대문자를 소문자로 접습니다. 조사가 붙은 한글에서도 입력 문자열을 그대로 찾고, 괄호·마침표 등도 문자 그대로 봅니다. 한 문단 내에서 중첩된 일치도 세며 문단 경계에서 새로 시작합니다. 자모 분해 표기와 유니코드 전체 대소문자 접기는 검색 범위 결정 때 다룹니다.

용어는 검색보다 엄격하게 판정합니다. `web/render.py`의 `link_terms_in_text`가 쓰는 `_doc_term_span`의 한글 낱말 시작, 동사 용법 배제, 한글 허용 공백, 라틴 경계를 데모에 재현했습니다. `수율이`는 잡고 `회수율` 속의 `수율`은 건너뜁니다. 선택 순서에서 앞선 용어가 겹친 범위를 가져가며, 다음 후보는 다른 등장 위치를 찾습니다. 운영에서는 구간 선택을 공통 함수로 추출해 기존 링크와 풀이가 같은 함수와 패턴을 호출하도록 합니다. 기존 브리프 링크의 선택 순서, 페이지별 `used`, 이스케이프 및 출력 바이트를 회귀 시험에 고정합니다. 새 조항 표면형이 필요한 경우 용어사전에서 검수해 별도 표면형 정책에 반영합니다. 괄호를 일괄 제거하면 서로 다른 개념이 같은 표면형이 될 수 있습니다.

## 접근성, 모바일, 성능

- **검색.** 검색 입력에 레이블을 붙이고 이전·다음에는 기본 버튼을 사용합니다. `aria-live="polite"`로 결과 번호를 알리며 이동 후에도 키보드 초점은 조작하던 곳에 둡니다. 한글 입력기 조합 중에는 검색을 미루고 조합이 끝난 문자열로 갱신합니다. CSS Custom Highlight API로 현재 결과와 나머지 결과를 구분합니다. 미지원 브라우저에는 기본 페이지 찾기 안내를 표시합니다. 운영 검증에서 고대비 모드, 결과 문맥을 보조기기로 읽는 흐름, 화면 확대 및 모바일 키보드가 열린 상태에서의 스크롤 위치를 확인해야 합니다.
- **용어 풀이.** 실제 버튼과 `aria-describedby`·`role="tooltip"`을 사용합니다. 정의에는 링크나 다른 초점 요소를 넣지 않습니다. 마우스로 풀이 위까지 이동할 수 있고, 키보드는 Tab으로 열고 Escape로 닫습니다. 모바일에서는 탭으로 고정하고 바깥 탭으로 닫습니다. 뷰포트 가장자리에서 좌우 위치를 제한하고 아래 공간이 부족하면 위에 배치합니다. 운영 HTML은 용어사전 링크를 기본으로 내보내고 JS가 준비된 뒤 버튼으로 활성화하면, JS가 실패해도 정의에 도달할 수 있습니다.
- **100KB급 페이지.** 공통 헤더와 다른 섹션을 제외하고 본문 문단만 인덱싱합니다. 본문 탐색은 한 번, 검색은 100ms 입력 지연 뒤 시작하며 현재 결과를 이동할 때는 같은 Range를 재사용합니다. 구간이 아주 많은 한 글자 검색은 Range 생성과 강조 비용이 늘어납니다. 운영 반영 전 100KB가 실제로 본문인 경우까지 포함해 저사양 모바일에서 건수, 입력에서 강조까지 시간, 스크롤을 측정합니다. 필요하면 Range 생성의 분할 처리나 가시 구간 렌더를 검토하고 전체 결과 건수와 이동은 유지합니다.
- **영문판.** 정적 제목과 버튼·레이블은 템플릿의 `_()` 키로 추가합니다. JS 문구가 필요한 자산에는 `web/grm_i18n.py`의 `JS_SHIM`을 바이트 그대로 넣고 `_t("한국어 원문 키", 슬롯)`을 사용합니다. `window.GRM_I18N` 사전은 영문판에서 자산보다 먼저 로드하며, 사전이 없어도 슬롯은 치환됩니다. 키는 `web/data/i18n/en.json`에 추가합니다. 정의는 본문 언어에 맞춰 `easy_ko` 또는 `easy_en`을 쓰며 필요한 언어의 정의가 비어 있으면 트리거를 생략합니다. 영문 페이지에서는 기존대로 원문을 표시하고, 원천이 한국어인 경우 본문의 언어 표기와 영문 UI를 검증합니다. 원문·번역·정의의 텍스트는 보존하고 UI만 변경합니다.

## 운영 반영 순서와 대상 파일

1. `web/render.py`의 공통 매칭 구간 선택을 추출하고 `web/clause_text_page.py` 및 조항 렌더 단계에서 문단 단위 구간과 일치한 정의를 구성합니다. 기존 `terms_by_href`의 조항별 관련 용어 칩은 그대로 활용합니다. `web/data/glossary.json`은 검수한 표면형이나 정의를 추가할 때만 수정합니다.
2. `web/templates/clause_text.html`에 본문 검색 범위, 접근 가능한 조작부, 용어 트리거를 넣습니다. `web/templates/partials/clauses_style.html`에는 항 내어쓰기, 강조, 풀이의 스타일을 넣습니다. `web/templates/clauses_doc.html`은 조항 목차에도 찾기를 제공하기로 결정하면 후속으로 연결합니다.
3. `web/assets/clause_find.js`, `web/assets/clause_tooltip.js`를 조항에서만 로드합니다. `web/data/i18n/en.json` 문구와 기본 템플릿의 사전 로드 순서를 확인합니다. 원문·번역 DOM 텍스트가 입력과 동일한지, HTML 이스케이프가 안전한지, 기존 링크와 `lang` 속성이 유지되는지 시험합니다.
4. 관련 조항·영문 트리·i18n 테스트와 영향받는 골든을 확인합니다. 키를 추가하면 저장소 규칙에 따라 영문 골든 5장을 `--freeze`로 갱신하고 `git diff --numstat`에서 예상한 해시 줄만 바뀌었는지 봅니다. 두 실제 스냅샷 및 본문 100KB 표본에 대해 모바일·키보드·스크린리더 검증 후 배포를 판단합니다.

## 대표가 정할 것

1. 첫 적용을 개별 조항의 원문·번역으로 할지, 문서 목차 검색도 함께 넣을지.
2. 풀이 표시를 각 언어의 첫 등장으로 할지, 반복에도 붙일지. 첫 등장은 밑줄과 Tab 정지 지점을 줄입니다.
3. 항 번호 내어쓰기와 강조까지 한 번에 적용할지, 두 기능을 먼저 적용하고 여러 원천의 항 구조를 검토한 뒤 적용할지.
