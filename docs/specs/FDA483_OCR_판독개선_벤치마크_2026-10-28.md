# FDA 483 OCR 판독 개선 — 벤치마크·채택안 (2026-10-28)

> 상태: **관찰 0건 문서의 전면 재판독 엔진을 tesseract CLI 로 채택·구현.** 범위는 **무료·로컬 방법만**이다(사용자 결정 2026-10-28 — 유료 클라우드 OCR·유료 LLM 비전은 쓰지 않으며 비용 설계도 하지 않는다).
> 구현: `collect_fda_483._full_ocr_fallback` / `_reocr_483_pdf_text` · 테스트: `tests/test_fda483_ocr_second_chance.py`.
> 같은 날 머지된 #1235(전면 OCR 폴백·PyMuPDF 내장 엔진 + 파서 보강) 위에 얹었다 — §3 참고.

## 1. 벤치마크 세트

| 세트 | 구성 | 출처 |
|---|---|---|
| 판독 실패 | Supabase `raw_signals`(source='FDA 483') 중 **findings 0건 + `fda483_excerpt` 있음 47건** 전수. 그중 이미지가 없는 디지털 원본 3건(106455·195404·195573 — 파서 문제)을 빼 **44건**을 OCR 벤치 모집단으로 썼다 | 원본 = raw_json `pdf_url` |
| 정상 판독 대조군 | findings ≥1 문서 60건(`md5(document_id)` 순 무작위). 그중 스캔본(1차 OCR 이 실제로 도는 문서) 11건을 엔진 비교의 회귀 세트로 따로 봤다 | 동일 |

측정 지표: 관찰 추출 수(`_extract_483_observations_from_text`) · 공개 게이트 통과 수(`_is_publishable_deficiency` — 추출 단계에서 이미 적용) · 깨짐(`_deficiency_garble` 기호 0·조각률 ≤0.08 인 관찰 수, `_text_corruption_ratio`) · 쪽당 시간.

- **idle 단일 프로세스 실측(20쪽):** 내장 경로 **4.15s/쪽**, CLI **3.41s/쪽**, CLI+OpenMP 4스레드 3.73s/쪽(이득 없음). 다른 프로세스와 CPU 를 나누는 상황에서 OpenMP 를 켜 두면 1쪽이 120s 타임아웃까지 늘어나는 것을 실측해 CLI 는 `OMP_THREAD_LIMIT=1` 로 고정했다.
- **기울기 보정**은 시험하지 않았다 — 순수 파이썬으로는 현실적인 속도가 안 나오고 numpy/opencv 의존성이 필요하다. tesseract 자체가 소각도 기울기를 흡수하며, 원본 대부분이 평판 스캔이다.
- **오픈소스 신경망 엔진**(PaddleOCR·docTR): CPU 1쪽 30s 이상 → 일일 예산 200쪽이면 100분으로 `grm-intake.yml` 55분 타임아웃을 넘는다. 설치 크기도 onnxruntime+opencv+모델 ≈ 650MB(venv 실측)이고 `requirements.txt` 에 ==pin 해야 할 전이 의존성이 10개 이상 늘어난다. **비채택.**
- 내장 경로와 CLI 가 같은 fast 모델인데 결과가 다른 이유: PyMuPDF 휠은 자체 빌드한 tesseract 를 번들하고, 페이지를 텍스트층으로 재구성해 붙이는 경로라 레이아웃 분석 입력이 다르다. CLI 쪽이 문서 5건 더 회수했다.

## 3. 채택안 — 관찰 0건 문서의 전면 재판독 엔진 = tesseract CLI

이 벤치 도중 #1235 가 머지됐다: "본문은 있는데 관찰 0건"이면 **모든 쪽을 PyMuPDF 내장 엔진으로
다시 판독**(`force_all`)하고 관찰이 나올 때만 채택한다(+ 1번 글리프 표제·깨진 마커 등 파서 보강).
구조가 같은 문제를 겨냥하므로, 별도 단계를 덧붙이지 않고 **그 전면 재판독의 엔진을 교체**한다.

```
_fetch_fda483_pdf_text
  ├─ 텍스트층 → (빈 쪽만) 내장 OCR                       ← 현행 그대로
  └─ 관찰 ≥1 → 반환(정상 문서 바이트 불변)
     관찰 0  → _full_ocr_fallback
                 tesseract CLI 로 모든 쪽 재판독         ← 이 PR
                 (CLI 가 없으면 내장 엔진 force_all — #1235 경로)
                 관찰 ≥1 → 재판독 텍스트(`pdf-ok-ocr`) / 0 → 원래 텍스트
```

- **왜 교체인가(연결이 아니라):** §2 에서 CLI 회수 문서는 내장 엔진 회수 문서를 **전부 포함**했다(CLI 만 회수 5건, 내장만 회수 0건). 내장 뒤에 CLI 를 덧붙이는 안도 측정했는데 실패 세트 OCR 이 159 → 215쪽(+35%)으로 늘면서 추가 회수는 실질 1건뿐이었다. 교체는 쪽수가 같다.
- **왜 1차(빈 쪽) OCR 엔진은 그대로인가:** 바꾸면 이미 관찰이 나오는 스캔본 1,500여 건의 텍스트가 재수집·재회수 때 바뀐다. 이득은 관찰 0건 경로에서 거의 다 얻는다.
- **엔진·모델 정본:** `.github/actions/setup-ocr` 가 이미 apt `tesseract-ocr`(바이너리)+`tesseract-ocr-eng`(fast)를 설치·검증한다(`command -v tesseract`). 워크플로 6종은 변경 없음. CI(`grm-ci.yml`)에도 이 액션을 붙여 실엔진 테스트가 러너에서 돈다.

### 3.1 전후 실측(실제 `_fetch_fda483_pdf_text`, 원본 PDF 로컬 대체, 4병렬)

| 세트 | #1235 이전 | main(#1235, 내장 엔진) | **이 PR(CLI)** |
|---|---|---|---|
| 판독 실패 47 — 관찰>0 문서 / 관찰 | 0 / 0 | 26 / 87 | **28 / 92** |
| 판독 실패 47 — OCR 쪽 / 시간 | 31쪽 / 106s | 159쪽 / 578s | **159쪽 / 468s** |
| 대조군 60 — 문서 / 관찰 | 60 / 369 | 60 / 371 | 60 / 371(**main 과 관찰 목록 전 문서 동일**) |

- main 이 회수하는 문서 중 이 PR 에서 관찰이 줄어든 문서: **0**. 추가 회수: 104952(1)·82880(1, 달걀 농장 — 범위 게이트에서 빠진다)·167686(2→3)·97849(6→8).
- 양쪽 다 회수한 12건은 표제 텍스트가 바뀐다. 대부분 개선이다 — 내장 엔진이 잃던 단어 사이 공백이 살아나고(`ofthe`→`of the`, `ofdrug`→`of drug`, 다수), main 이 161809 에서 표제로 내던 양식 잡음("aot CRD IS Fo) Gel | ewrucrese …")이 사라진다. CLI 는 단어 끝 `l` 을 `!` 로 읽는 일이 잦아("quality contro! unit") 관찰 파서가 거기서 표제를 잘랐고, 잘린 표제 2건(191121 "…quality contro!", 161809 "…used for the!")이 **공개 게이트 `_is_publishable_deficiency` 를 통과해 관찰로 저장되는 것을 확인**했다. 게이트·파서는 그대로 두고 **CLI 출력에만** `_repair_cli_bang`(글자 뒤 `!` 다음이 소문자로 이어질 때만 — 앞 단어가 기능어면 `!` 삭제, 아니면 `l`)을 걸었다 → 두 표제가 "…quality control unit are not fully followed." · "…used for the manufacturing processes …"로 온전해졌고, 그 밖의 관찰은 바이트 단위로 같다. 161811 "Devialbon investigations are inadeguate"는 남는다(철자 오독). 엄격 게이트(`_is_recovered_deficiency_publishable`) 통과: main 86/87 → 이 PR 91/92.

### 3.2 시간·예산

- idle 단일 프로세스 실측(20쪽): 내장 엔진 **4.15s/쪽**, CLI **3.41s/쪽**. 쪽수가 같으므로 관찰 0건 경로의 벽시계는 줄어든다(벤치 4병렬 −17%).
- 재판독은 1차 OCR 과 **같은 페이지 예산**(`_OCR_BUDGET`: 일일 200쪽 · 월요일 버스트 600쪽 · 회수 600쪽)과 문서당 30쪽 상한을 쓴다 → **최악 벽시계는 늘지 않는다**(200쪽 × 4.15s ≈ 14분 상한 그대로). `grm-intake.yml` 55분 타임아웃·월요일 마감(06:45 KST, `FDA483_BURST_DEADLINE_EPOCH`) 계산에 변화 없음.
- 일일 실측(grm-intake 최근 7회, 10-20~10-27): OCR **71·200·195·200·119·200·117쪽**, 수집 스텝 14~27분.
- 관측: health `fda_483_ocr.reocr_tried`·`reocr_adopted`, 수집 로그 `전면재판독=채택/시도`.

## 4. 남은 한계

- **판독 실패 47건 중 19건은 여전히 0건**(100536·105088·115117·170404·184979·193617·195404·195467·195490·70669·70695·78612·82754·82835·82853·82887·82949·83012·99495). 대부분 본문은 읽히는데 관찰 마커/번호가 깨지거나 옛 양식이라 파서의 몫이다 — 관찰 파서는 다른 세션 범위라 손대지 않았다.
- **현행 공개 게이트를 통과하는 OCR 잡음**이 있다(게이트는 바꾸지 않았다): 79336 양식 머리말이 표제로 잡힘, 161811 "Devialbon … inadeguate". (`!` 로 잘린 표제 2건은 CLI 출력 수리로 해소 — §3.1.) `pdf-ok-ocr` 텍스트에 엄격 게이트를 거는 것은 파서 측 후속 과제다.
- 원본 144dpi 스캔의 정보 한계 — 업스케일·이진화로 회수 문서 수가 늘지 않았다. 기울기 보정은 의존성(numpy/opencv) 때문에 시험하지 않았다.
- GitHub 러너 실측은 CI 의 실엔진 테스트 1건(1쪽)뿐이다. 수집 규모의 러너 시간은 기존 일일 로그(내장 엔진 기준)로 상한을 잡았다.

## 5. 재현

벤치 하네스는 저장소 밖(세션 스크래치)에서 돌렸다 — 핵심 절차만 남긴다: ① 위 SQL 로 대상 `document_id` 추출 ② `https://www.fda.gov/media/{id}/download` 로 원본 수령 ③ `http_get_bytes` 를 로컬 바이트로 대체하고 `_fetch_fda483_pdf_text` → `_extract_483_observations_from_text` 실행(수정 전 = `main` 워크트리, 수정 후 = 이 브랜치) ④ 엔진 비교는 이미지 페이지를 강제 재판독하며 엔진·모델(`tessdata_fast`/`tessdata_best`/legacy)·DPI·psm·전처리를 바꿔 같은 지표로 집계.
