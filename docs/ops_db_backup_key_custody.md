### 지금 무엇이 위험한가 (3줄)
1. 개인키가 회사 PC 한 곳에만 있다. 그 PC 가 고장·반납·초기화되면 **백업 13개 전부가 열리지 않는 자물쇠 상자**가 된다.
2. Supabase 무료 플랜은 자동 백업이 없어서, 이 백업이 사실상 유일한 두 번째 사본이다(원문 저장소 `raw_signals` 의 상당수는 다른 곳에 사본이 없다).
3. 복원을 한 번도 해 보지 않았다. 열쇠가 있어도 "실제로 되살아나는지" 는 아직 모른다.

### 확인 필요 (지어내지 않음)
- 개인키에 **비밀번호(패스프레이즈)가 걸려 있는지**. 걸려 있다면 그 비밀번호도 열쇠와 함께 보관해야 한다. (열쇠 파일은 열어 보지 않았다.)
- 개인키의 **개인 PC 쪽 복사본 존재 여부**. 이관 전에 확인.
- 비밀번호 관리자 종류·가족/동료 공유 가능 여부 (대표 선택).
- 개인 PC 에 Docker 또는 Postgres 17 이 설치돼 있는지.
- 최근 아티팩트 크기와 복원 소요 시간.

## 1. 열쇠를 두 번째 안전한 곳에 보관하기

원칙: **서로 다른 종류의 장소 두 곳 이상**, 어느 한 곳을 잃어도 복구 가능. 전부 무료.

| 사본 | 장소 | 형태 | 누가 |
|---|---|---|---|
| A | 회사 PC (현재) | `.SECRET.asc` 파일 | 이미 있음 |
| B | 비밀번호 관리자(예: Bitwarden 무료 등)의 **보안 메모** | 파일 내용 전체를 메모에 붙이거나 첨부 | **대표** |
| C | 종이 인쇄본 + 금고(또는 잠기는 서랍) | 아래 3단계 참고 | **대표** |
| D (선택) | 암호화 USB 한 개를 다른 장소(집 등)에 | 파일 복사 | 대표 |

### 단계
1. **(대표) 파일을 안전하게 꺼낸다.** 회사 PC 의 `private/credentials/db-backup-gpg/grm-db-backup.SECRET.asc` 를 비밀번호 관리자 앱이 있는 기기로 옮긴다. 메일·메신저·일반 클라우드 폴더로 보내지 않는다. USB 로 직접 옮기고 끝나면 USB 의 파일을 지운다.
2. **(대표) 비밀번호 관리자에 저장.** 새 "보안 메모"를 만들고 제목을 `GRM DB 백업 개인키 (지문 앞 8자리 23C48C10)` 로 한다. 파일 첨부 또는 본문 붙여넣기. 개인키에 비밀번호가 걸려 있으면 **같은 항목에** 비밀번호도 적는다.
3. **(대표) 종이 인쇄본(권장).** 비밀번호 관리자 계정 자체를 잃는 경우 대비. 개인키 파일을 인쇄해 봉투에 넣어 금고에 둔다. 봉투에는 "GRM DB 백업 열쇠, 지문 앞 8자리 23C48C10" 만 적는다.
4. **(대표) 비밀번호 관리자의 마스터 비밀번호·복구 코드**도 별도 종이에 적어 금고에 둔다(이것이 없으면 B 도 못 연다).
5. **(비서가 할 수 있는 것)** 이 문서·복원 시험 양식 준비, 시험 시 명령어 안내, 결과 기록. **비서는 열쇠 파일을 읽거나 옮기지 않는다.**
6. **(대표) 보관 확인.** 비밀번호 관리자에서 꺼낸 사본으로 §2 복원 시험의 "복호화" 단계까지 해 본다. 여기서 풀리면 B 가 진짜 열쇠라는 증명이다. 종이 사본 C 는 연 1회 존재만 눈으로 확인.
7. 완료 후 `docs/ops_runbook.md` §6 변경 이력에 "열쇠 2곳 보관 완료 YYYY-MM-DD" 한 줄(장소 종류만, 값 없이).

### 하지 말 것
- 열쇠를 이 저장소·이슈·PR·채팅·메일 본문에 올리지 않는다(공개 저장소다).
- 열쇠와 백업 파일을 같은 곳에 두지 않는다(같이 유출되면 데이터가 열린다).

## 2. 복원 시험 절차 (개인 PC 이관 뒤 1회, 이후 분기 1회)

예상 소요: 처음엔 도구 설치 포함 1~2시간, 익숙해지면 30분 안팎(데이터 크기에 따라 다름, 확인 필요). 비용 0.
**운영 DB(Supabase)에는 절대 복원하지 않는다.** 시험은 항상 새 임시 DB 에서, Supabase 새 프로젝트가 아니라 **로컬 Postgres** 로 한다.

### 준비물
- 내려받은 아티팩트(GitHub → Actions → `GRM DB Backup` → 최근 성공 실행 → Artifacts 의 `grm-db-<날짜>`; zip 안에 `grm-db-<날짜>.tar.gz.gpg`)
- 개인키 사본(§1 의 B, 이관 후 PC 에서 꺼낸 것)
- `gpg`, Docker(`pgvector/pgvector:pg17` 이미지) 또는 pgvector 가 설치된 Postgres 17
- 작업 폴더는 **빈 새 폴더**(예: `restore-test-YYYYMMDD`). 시험 후 통째로 삭제.

### 단계
1. **받기.** 최근 성공 실행의 아티팩트를 내려받아 zip 을 푼다. 실행 요약 탭의 "행 수 대조 리포트"도 저장(비교 기준).
2. **임시 키링으로 열쇠 가져오기.** 기본 키링을 건드리지 않도록 시험용 폴더를 쓴다.
   `gpg --homedir ./gpg-tmp --import grm-db-backup.SECRET.asc` (비밀번호를 물으면 §1-2 에 보관한 것).
3. **복호화.** `gpg --homedir ./gpg-tmp --output grm-db.tar.gz --decrypt grm-db-<날짜>.tar.gz.gpg`
4. **풀기.** `tar xzf grm-db.tar.gz` → `schema.sql`, `data.sql`, `counts.json`, `verify_report.md`.
5. **임시 DB 띄우기.** `docker run --rm -d --name grm-restore -e POSTGRES_PASSWORD=<임시값> -p 55432:5432 pgvector/pgvector:pg17` (임시값은 아무 값이나, 컨테이너와 함께 사라짐). 필요하면 `create extension vector;`.
6. **스키마 적용.** `psql -h localhost -p 55432 -U postgres -f schema.sql` — `ON_ERROR_STOP` 은 끈다. auth·확장 참조 오류는 정책·트리거 수준이라 표 생성엔 영향 없다(런북 §6). 오류 줄 수를 기록.
7. **데이터 적용.** `psql -h localhost -p 55432 -U postgres -f data.sql`
8. **검증(핵심).** 표별로 **복원 DB 의 정확한 `count(*)`** 를 구해 다음 둘과 대조한다.
   - `counts.json` (백업 직전 라이브 정확 count)
   - `verify_report.md` 의 COPY 행 수(덤프 파일 안 행 수)

   **504 주의:** 라이브 정확 count 가 타임아웃(PostgREST 504)이면 백업이 `count=planned` 추정치로 대체한 표가 있고 리포트에 `~` 로 표시된다(`counts.json` 의 `__approx__` 목록). 이 표는 `counts.json` 과 정확히 같지 않은 게 정상이다. 이 표는 **COPY 행 수 = 복원 DB `count(*)`** 일치로 판정한다. 나머지 표는 라이브 count 와 99% 이상 일치(백업 워크플로 기준 `--min-ratio 0.99`)하고 COPY 행 수와는 같아야 한다. 백업 이후 새로 들어온 행 때문에 라이브와 약간 어긋날 수 있다.
9. **눈으로 확인.** `raw_signals`, `findings` 에서 최근 행 몇 개를 조회해 한글이 깨지지 않았는지 확인(UTF-8).
10. **정리.** `docker rm -f grm-restore`, 작업 폴더·복호화된 평문·임시 키링 삭제(평문 덤프에는 사용자 표가 들어 있다). 개인 PC 라면 휴지통까지 비운다.
11. **기록.** 아래 양식을 채워 `docs/ops_runbook.md` §6 변경 이력에 한 줄(날짜·합격/불합격·소요) 남긴다.

### 합격 기준
- 복호화 성공, `tar` 정상, 스키마 적용 후 표 수가 `verify_report.md` 의 표 수와 같음.
- `raw_signals`·`findings` 포함 모든 표가 8번 기준 통과(0행 표는 라이브도 0행일 때만 통과).
- 실패하면 실패 지점(어느 단계)과 오류 첫 줄을 기록해 비서에게 전달(열쇠·비밀번호는 전달하지 않는다).

## 3. 열쇠를 잃었을 때

- **모든 사본을 잃은 경우, 기존 백업(최대 13개)은 복구 불가능**하다(공개키 암호화의 성질). 되살릴 방법은 없다.
- 앞으로를 지키려면 **열쇠 교체**를 한다.
  1. 새 GPG 키 쌍을 만든다(운영자 PC 에서 `gpg --quick-generate-key`, ed25519, 필요 시 비밀번호). 새 개인키는 §1 방식으로 **즉시 2곳 이상** 보관.
  2. 새 공개키를 `gpg --armor --export <지문>` 으로 내보내 `.github/db-backup-gpg.pub.asc` 를 교체.
  3. `.github/workflows/grm-db-backup.yml` 의 `EXPECTED_FPR` 를 새 지문으로 교체(두 값이 다르면 워크플로가 일부러 실패한다). **이 두 파일은 한 PR 에서 같이 바꾼다.**
  4. 머지 후 Actions → `GRM DB Backup` → Run workflow 로 수동 백업 1회(`label` 예: `new-key`) → 성공 확인 → §2 복원 시험으로 새 열쇠 검증.
  5. 옛 열쇠가 살아 있다면(의심 유출 등) 옛 아티팩트는 옛 열쇠로 열린다. 옛 아티팩트는 90일 뒤 자동 삭제되므로 그 사이 필요한 것은 새 열쇠 백업으로 대체.
- 2~3번 코드 수정은 비서가 PR 로 준비할 수 있으나, **새 개인키 생성·보관은 대표가 직접** 한다.
