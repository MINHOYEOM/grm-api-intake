# 실행 규칙 — 브리프편집팀이 월요일 실제 발행을 맡는다 (2026-W45 부터, 대표 결정 2026-10-31)

> **이 파일은 다음 판(시범) 지시문이다 — 실제 월요일 발행은 `company/editorial/RUN.md` 을 읽는다.**
> 리허설(`company/editorial/REHEARSAL.md`)만 이 폴더(`company/editorial/next/`)를 읽는다. 전환 때 이 내용이 실발행 파일로 옮겨진다.
> 이 파일 안에서 `RUN.md`·`desk.md`·`reporter.md`·`copyedit.md` 라고만 적힌 곳은 같은 폴더(`next/`)의 파일을 뜻한다.

데스크(07:20, 재시도 07:45) → 기자 워커 풀(08:00, 보강 08:40 · 샤드 수 가변) → 교열(1차 08:45 · 재작업 09:02 · 2차 09:12) 순서로 돌고, **교열이 통과시킨 것만** 발행 경로에 넘긴다.
**자동 백업은 없다** — v16 Routine(09:30)은 Notion 을 발행 길에서 뺄 때 꺼졌다(0항). (2026-11-02 시범에서 handoff 가 07:05 에야 생기고 기자 한 세션이 분량을 못 감당해 시각표·분량을 바꿨다 — 아래 5·6항.) 이 파일의 규칙은 직무 지시문과 v16 본문보다 **우선한다.**

## 0. 이번 호의 길 (사람이 바꾸는 두 줄 — 전환한 호부터)
- `handoff 길: git` — handoff 를 저장소 브랜치 `claude/queue-handoff` 의 파일에서 읽는다(2항). 수집기가 DB 로 만든 것이다.
- `반납 길: git` — 교열이 통과시킨 델타는 실행 폴더에 push 한 파일이다. 발행 브릿지가 가져간다(`copyedit.md` 마감). 이 줄은 더 바꾸지 않는다.
- **Notion 은 발행 길에 없다**(대표 결정 — 11-23 호 편집팀 발행 성공 뒤). 어떤 직무도 Notion 을 읽거나 쓰지 않는다.
- **편집팀 직무는 백업을 기다리거나 부르지 않는다** — 이 파일의 "자동 백업은 없다"는 그 뜻이다. v16 백업 Routine(월 09:30)은 꺼졌고,
  그 자리는 **백업 v17**(`company/editorial/backup.md`, 월 09:30 · 별도 Routine)이 맡는다: 발행 브릿지가 편집팀 반납을 쓸 수 없을 때만 같은 브랜치의
  `company/run/{D}/backup/` 에 따로 반납한다(편집팀 파일은 건드리지 않는다). 백업도 못 넘긴 호는 종합상황실 10:45 확인(`company/situation-room/brief-prep.md`)이
  `★델타 없음` 으로 잡고 대표가 정한다. 그래도 품질 기준은 그대로다: 통과가 아니면 반납하지 않는다.
- 리허설(실제 발행 없이 같은 순서를 돌려 보는 것)은 `REHEARSAL.md` 가 이 파일보다 우선한다.

## 1. Notion 은 읽지도 쓰지도 않는다
- 데스크·기자·교열 모두 Notion 의 어떤 페이지·속성도 읽거나 만들거나 바꾸지 않는다. handoff 도, 마감 표시도 저장소에 있다.
- 행마다의 Status 는 DB 대기열(`intake_queue`)이 발행 결과로 스스로 계산한다(수집기·`grm_queue.py`). 교열이 찍을 것은 없다.
- 하나라도 통과가 아니면 교열은 반납하지 않고 끝낸다. 품질이 떨어지는 글이 발행 길에 들어가지 않게 하는 안전장치다.

## 2. handoff 선택 = 저장소 파일 (날짜·요일 규칙은 v16 [0단계] 그대로)
```
D=<이번 주 월요일 KST, YYYY-MM-DD>; mkdir -p _handoff
git fetch origin claude/queue-handoff && git show FETCH_HEAD:handoff_$D.json > _handoff/handoff_$D.json
```
- 파일이 없거나 비어 있으면 데스크는 5-2항 시한까지 기다리고, 그래도 없으면 `상태: 보류` 로 종료한다(수집이 아직 안 끝났거나 DB handoff 생성 실패 — 자동 백업은 없다). 다른 날짜의 파일로 대신하지 않는다.
- 그리고 이 호가 이미 발행 길에 들어갔는지 본다: `git fetch origin main && git show FETCH_HEAD:web/data/deltas/delta_$(echo $D | tr - _).json` 이 성공하면(이미 있다) `상태: 보류`(이미 누가 처리했다는 뜻). Notion 은 보지 않는다.
- 이 파일의 `rows[]` 가 유일한 입력이다. 행에 Notion `page_id` 는 없다(쓰지 않는다). 카드 키는 `web_card_id`.
- 월요일 파일은 **07:00 KST 부터 동결**된다 — 그 뒤에 수집을 다시 돌려도 바뀌지 않는다(그 전의 재실행은 갱신한다). 그래서 데스크·기자·교열이 같은 파일을 본다.

## 3. 중간 결과는 git 브랜치에
- 브랜치: `claude/company-{run_date_kst}` (예: `claude/company-2026-11-02`). 아래 순서로 올라탄다(`B` = 브랜치 이름).
  ```
  if git fetch origin "$B"; then git checkout -B "$B" FETCH_HEAD; else git fetch origin main && git checkout -b "$B" FETCH_HEAD; fi
  ```
  - **`origin/main` 이라는 이름을 쓰지 않는다.** 실행 환경에 저장된 `origin/main` 은 며칠 전 것일 수 있다(2026-11-13 리허설: 11-06 커밋이었고,
    거기서 브랜치를 만들자 이 폴더와 `handoff_ref.py` 가 사라졌다). 새 브랜치는 반드시 방금 `git fetch origin main` 한 `FETCH_HEAD` 에서 만든다.
  - 브랜치에 올라탄 직후 `test -f company/editorial/handoff_ref.py` 를 확인한다. 없으면 낡은 커밋 위에 있는 것이다 — 아무것도 쓰지 말고 `상태: 실패`, 사유 `낡은 main 에서 만든 브랜치` 로 종료한다.
- 폴더: `company/run/{run_date_kst}/` 에 직무별 파일만 쓴다. 다른 경로는 건드리지 않는다.
- 기자 샤드는 **같은 브랜치에 동시에** 쓴다. 각자 자기 파일만 `git add <파일>` 로 커밋하고, push 전에 `git pull --rebase origin claude/company-{run_date_kst}`,
  push 가 거절되면 같은 방식으로 3번까지 다시 시도한다. 그래도 안 되면 `보류`.
- PR 을 열지 않는다. `main` 에 push·머지하지 않는다. (발행 PR 은 기존 자동화가 만든다.)

## 4. 한도는 현행과 같게
- WebSearch 총 9회 · WebFetch 5회 (v16 [1단계]).
- 다른 직무의 결과를 고치지 않는다. 이의가 있으면 자기 파일에 `이의:` 한 줄로 남긴다.
- 앞 직무 파일이 없거나 `status` 가 `완료` 가 아니면 `보류` 로 종료한다 — 자동 백업은 없다 — 종합상황실이 잡고 대표가 정한다(0항).
  (예외: handoff 가 늦을 때 데스크·워커가 시한까지 기다리는 것 — 5-2항.)

  09:02~09:20 의 18분 안에 재작업과 2차 교열(다시 합치기·코드 검사 약 2분 · 반려 카드 재판정 · 칸 삭제 반영 뒤 코드 검사 다시 약 2분 · 마감 push)이 다 들어가야 한다.

### 5-2. handoff 가 늦을 때 — 데스크·기자가 기다린다 (2026-11-16 대표 결정)

- **handoff 를 읽을 수 있음** = 저장소 파일 `claude/queue-handoff:handoff_{D}.json` 이 있고 `handoff_ref.py` 가 exit 0 이다(2항). Notion 은 보지 않는다. 사본은 수집이 끝나고 몇 분 뒤에 올라온다 — 없으면 다음 확인까지 기다린다.
- **데스크 잠금** — handoff 를 찾으면 일을 시작하기 **전에**, 3항 브랜치에 올라탄 뒤 `python company/editorial/shard_claim.py claim company/run/{D} desk desk "데스크 07:20"`
  (07:45 슬롯은 `"데스크 07:45"`). exit 0 = 내가 맡음. exit 1 = 다른 데스크가 하는 중 — `python company/editorial/shard_claim.py desk company/run/{D}` 가
  `done` 이 될 때까지 5분마다 확인하고(시한은 위 표와 같다), `stale`(맡은 지 25분이 넘도록 `desk.json` 이 `완료` 가 아님)이면 다시 claim 해 이어받는다.
  07:20 데스크가 07:42 직전에 handoff 를 찾아 일하는 중에 07:45 데스크가 와도 둘이 같은 일을 하지 않는다.
- 데스크는 08:10 이 지나서 처음 handoff 를 찾았으면 시작하지 않는다(기자·교열 시간이 모자란다) — 위 `보류`.
- 워커는 `desk.json` 이 `보류`·`실패` 면 기다리지 않고 바로 종료한다. 파일이 없거나 그 밖의 상태면 기다린다.
- 대기는 `sleep` 을 **한 번에 90초 이하**로 나눠서 한다(Bash 도구 기본 시한 120초 — 그보다 긴 명령은 잘리고, Routine 세션은 긴 `sleep` 을 막기도 한다).
  '5분마다'·'3분마다'는 확인 간격이지 `sleep` 한 번의 길이가 아니다(예: 5분 = `sleep 90` 을 네 번 남짓). 기다리는 동안 다른 일(검색·작성)은 하지 않는다. 확인할 때마다 `git fetch` 로 새로 받는다.
  워커 루프(7항)는 `check --wait` 이 파이썬 안에서 기다리므로 `sleep` 을 따로 하지 않는다.
- 기다리는 동안 handoff 가 바뀌지 않는다: 07:00 KST 이후 수집을 다시 돌려도 그날 handoff 가 이미 있으면 다시 쓰지 않는다
  (`grm_handoff.publish_day_handoff_frozen` · DB 사본도 같은 규칙). 그래서 데스크가 읽은 handoff 를 기자·교열도 그대로 본다.
- 어림(분량은 그 주마다 다르다): handoff 08:10 → 데스크 약 15분 → 워커 08:25 시작 → 첫 샤드 08:50 전후 → 7항의 08:55 이후엔 새 샤드를 잡지 않으므로
  샤드가 워커 수보다 많은 주는 교열 시한(09:20)에 못 맞춰 반납하지 못한다(자동 백업은 없다 — 종합상황실이 잡고 대표가 정한다).

## 6. 기자 일의 분할 — 샤드 수는 분량이 정한다 (가변, 카드는 줄이지 않는다)
- 데스크는 입력 JSON `{"delta":[web_card_id…(handoff 순서)],"deep":[{"id":…,"obs":483 관찰 건수}…]}` 를 만들어
  `python company/editorial/plan_shards.py <입력.json> --handoff _handoff/handoff_{D}.json` 을 돌리고, 출력 `shards` 를 `desk.json` 에 **그대로** 넣는다(LLM 이 나누지 않는다).
  형태: `{"delta":{"A":[…],"B":[…],…},"deep":{"A":[…],…},"tldr":"T"}` — 샤드는 A, B, C… 로 늘어난다(델타 상한 8 · 심층 상한 16, 최소 2).
  delta 는 `action=render`·`merged_into` 없음 카드를 handoff 순서의 **연속 구간**으로 균등 분할(샤드당 약 18장 이하),
  deep 은 `deep_analysis_ready`·`ncr_translation_ready` 카드를 샤드당 12장·483 관찰 30건·원문 6만 자 이하로 균형 분할한다(원문 글자 수는 `--handoff` 로 센다 — 실측 12.5만 자 샤드 약 8분, 25분 점유 안에 끝나는 크기).
  **FDA 게시 기준 카드는 전부 싣는다** — 모자라면 샤드가 늘 뿐 카드를 덜어내지 않는다(`plan_shards.py` 가 상한 초과 시 경고만 낸다).
- 샤드 하나는 자기 목록의 카드**만** 쓴다. 결과는 `delta.{S}.json` · `deep.{S}.json` 과 가상 샤드 `delta.T.json`(브리프 `tldr`·`tldr_en`) — 형태는 `reporter.md`.
- `T` 는 **모든 델타 샤드가 `완료`가 된 뒤** 한 워커가 한 번 쓴다(각 샤드의 `title_issue` 를 읽는다). 델타 샤드 사이는 서로 기다리지 않는다.
- 이미 자기 결과 파일이 `완료`로 있으면 일을 다시 하지 않는다(재실행 안전).
- 합치기는 LLM 이 하지 않는다: 교열이 `python company/editorial/merge_parts.py company/run/{run_date_kst}` 를 돌려
  `delta.json`·`deep_delta.json` 을 만든다(샤드 이름은 `desk.json` 계획에서 읽는다). 계획과 한 장이라도 다르면 exit 1 → 교열 `보류`(편집팀 안 이어받기 없음).

## 7. 끝날 때까지 이어서 한다 — 워커 루프와 잠금 (`shard_claim.py`)
워커 한 개가 한 샤드로 끝나지 않는다. 자기 일을 끝내고 시간이 남으면 다음 빈 샤드를 가져온다.
```
반복:
  python company/editorial/shard_claim.py check company/run/{D} <delta|deep> <워커이름> --until 08:55 --wait   # 끝내도 되는지 코드가 정한다
  exit 0(DONE · DEADLINE · NO_TAKEOVER)이면 종료. exit 1 이면 끝내지 않는다:
    WAIT <S> <초> → 셸 `sleep` 없이 **같은 명령을 곧바로 다시** 실행 — `--wait` 이 파이썬 안에서 이미 최대 90초 기다렸다(한 번 실행이 120초 시한 안에 끝난다).
                    남이 잡은 샤드가 죽은 것으로 판정되면 이어받는다
    CLAIM <S>     → 아래로
  python company/editorial/shard_claim.py claim company/run/{D} <종류> $S <워커이름>   # 0=내가 잡음, 1=졌음 → 위로 돌아가 다음 샤드
  샤드 S 를 처리하고 결과 파일을 커밋·push (RUN.md 3항 방식) — 이것이 곧 '완료' 표시다
```
- **잠금** = `company/run/{D}/claims/{종류}.{S}.claim` 파일을 커밋해 push. push 가 거절되면 `pull --rebase` 후, 같은 파일이 남의 것이면 진 것이다(3번 재시도).
- 점유한 지 25분이 지나도록 결과 파일이 없으면 **죽은 워커**로 보고 다른 워커가 가로챈다. 한 샤드가 25분 안에 끝나지 않는 크기이면 안 되므로 샤드 한도(6항)를 그에 맞춰 둔다.
- 자기 결과를 쓰기 직전에 `desk.json` 의 목록과 자기 카드가 같은지 확인한다. 못 끝낸 샤드는 부분 결과를 `완료`로 쓰지 말고 `claim` 만 남겨 둔다 — 25분 뒤 보강 워커가 이어받는다.
- **끝내는 조건은 `check` 의 exit 0 하나뿐이다.** 분량(원문 글자 수)·문맥 크기·'한 워커가 많이 못 가져간다'는 판단은 끝낼 이유가 아니다 —
  빈 샤드를 남기고 끝내면 그 샤드는 아무도 하지 않아 그 호가 반납되지 않는다(편집팀 안 이어받기 없음 — 리허설 1120g: 심층 워커가 7개 중 2개만 하고 끝냈다). 끝낼 때 마지막 `check` 출력 한 줄을 보고에 적는다.
  끝낸 샤드의 원문은 다시 읽지 않는다 — 다음 샤드는 그 샤드 카드만 읽는다.
- `T` 는 08:55 시한에서 빠진다 — 델타 본 샤드가 모두 `완료`이고 `T` 만 비어 있으면 08:55 뒤에도 `check` 가 `CLAIM T` 를 낸다(T 가 비면 합치기가 멈춰 그 호가 반납되지 않는다).
- 델타 워커는 Opus, 심층 워커는 Sonnet — **종류가 다른 샤드는 가져오지 않는다**(모델 배정을 지킨다).
- 서브에이전트·병렬 세션은 쓰지 않는다(`CHARTER.md`). 분량이 늘어도 해법은 '샤드를 늘리고 워커 슬롯에 중복 배치'이지 세션 안에서 병렬화가 아니다.
- 예약작업이 다른 예약작업을 깨우거나 세션을 새로 여는 길은 **이 저장소에서 실측하지 못했다**. 확인되면 이 항을 고친다 — 그 전까지는 고정 슬롯(5항)만 쓴다.

## 8. 월요일 handoff 를 다시 만들어야 할 때 (사람만 — 편집팀 직무는 하지 않는다)
- **07:00 KST 전**: 수집을 다시 돌리기만 하면 된다(`GRM API Intake (Daily)` 재실행). 그 시각 전의 재실행은 월요일 파일을 스스로 갱신한다
  (FDA 483 본문 회수 뒤의 자동 재생성 `grm-fda-coverage-gate.yml` 도 이 길이다).
- **07:00~07:20**(파일은 동결됐고 데스크는 아직 읽기 전): 저장소 변수 `GRM_QUEUE_HANDOFF_REFRESH=true` → 수집 재실행 → 끝나면 변수를 `false` 로(이 스위치 하나가 둘 다 푼다).
- **07:20 뒤에는 다시 만들지 않는다**(직무마다 다른 파일을 보게 된다). 이미 발행돼 닫힌 호에는 스위치도 듣지 않는다.
